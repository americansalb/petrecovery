Are we ready to launch?

A launch-readiness audit of ReunitePets, run against the code that ships to reunitepets.org — built, seeded, and driven in a browser rather than read.

Status

All 39 findings fixed.

The audit below found seven blockers, nineteen high and thirteen medium issues. Every one has been fixed on claude/reunitepets-launch-audit-1u0h0i, each verified against a running build rather than by reading the diff. The findings are left as originally written — the record of what was wrong is worth more than a tidy document.

Gates at the end: 687 tests across 62 suites (up from 591 in 51), production build clean, and ESLint passing. ESLint had never run here — no config existed, and the CI step ended in || echo, so it could not fail. Its first real pass found four genuine bugs, including a file that plain node refuses to parse.

Six things were worse than this report said

Found only by fixing it. Each was invisible from reading the code.

  1. instrumentation.js never ran at all. Next 14 needs experimental.instrumentationHook, which was not set — so every boot assertion in that file was dead code that looked live, including the production error-sink check added earlier in this same audit.
  2. The CAPTCHA verifier returned success when unconfigured. Wiring the unused verifier in as it stood would have changed nothing at all.
  3. The unsubscribe path had never been walked. The success page it redirects to did not exist, the redirect pointed at the retired domain, and its POST handler would have thrown on the one-click request Gmail and Outlook actually send.
  4. The Terms, Waiver and Privacy Policy all named the wrong company — and the waiver and policy lived inline in the seed script, which production never runs, so no deploy could ever have corrected them.
  5. "Delete Account" could not be a user.delete(). Two cascade rules meant the obvious implementation would have erased active searches other people were out running.
  6. /join had no waiver gate while every other route into the same activity had one — which made the waiver optional in practice, through the easiest door.

Two claims in this report were wrong

Corrected in place rather than quietly dropped.

  1. H1 said /api/reports/create had no rate limit. It had one, predating this work. The real problem was worse and less obvious: the limiter was per-process and in-memory, so it forgot everything on every deploy. That is how 87,003 junk rows got past a cap set to 10 per minute.
  2. M9's "the drawer lists Pet Care twice" needed a second look. The first check counted the bottom tab bar and came back clean. Opening the drawer properly showed it was real.

The four that matter most

Ranked by how much damage they do before anyone notices.

  1. An unauthenticated API hands out every reporter's name, phone and email — in bulk, to anyone who asks. That is a scraper's list of distressed pet owners, the exact population targeted by "I have your pet, send money" scams. The team already fixed this same bug class once, on a sibling route, and wrote a regression test for it.
  2. The city landing pages publish randomly generated "Pets Reunited" numbers that change on every refresh. These pages are public, indexed, and are where Google sends someone searching "lost dog austin".
  3. An anonymous stranger can file a lost-pet report under any existing account just by typing that person's email address — publishing a fabricated case in their name, with their address then exposed by the first bug.
  4. On a phone, the "I've Seen Max" button is not clickable — the global tab bar is painted over it. That is the product's core loop failing on the device most people use.

How this was checked

The production domain was not reachable from this environment. Requests to www.reunitepets.org return 403 from the network policy's egress gateway. So this audits the code that ships to that domain, exercised by running it: PostgreSQL 16 seeded from the repo's own fixtures, the dev server, and a browser driving both.

Anything depending on production configuration — whether the email key is set, the real shelter dataset, true response times under load — is out of scope and flagged where it matters.

Subagents swept for candidates in two passes. A visual review read the screenshots across 7 batches and ran to completion, deflating 87 raw observations to 47. A code audit swept 13 dimensions and produced 118 raw candidates; its per-finding verification stage did not finish — roughly 100 high-effort verifier agents against a ~12-wide concurrency cap — and was stopped. Nothing here rests on it.

Every finding below was reproduced by hand — by reading the code, by curl, by measuring the live DOM, or by querying the database. That is the guarantee, and it holds regardless of what the subagents finished: they were used to find candidates, never to confirm them. Five claims did not survive my own check and were cut; they are listed at the end rather than quietly dropped.

Blockers

Each one reproduced first-hand. Open a row for the evidence.

B1An unauthenticated API publishes every reporter's name, phone and email▸

app/api/public/missions/[caseNumber]/route.js:193-206. There is no session check anywhere in the 255-line file.

Reproduced, no cookie

$ curl .../api/public/missions/AUS-2026-0001
"contact": {
  "name":  "Avery Admin",
  "phone": "512-555-0100",
  "email": "admin@localdev.test"
}

It is bulk-harvestable: the sibling list endpoint — also unauthenticated — enumerates every case number, so two calls per victim yield the whole list. The response also returns unfuzzed coordinates, and there is no location-fuzzing helper anywhere in the codebase.

Three things make this a blocker rather than a design decision:

— The current product deliberately does the opposite. The canonical case page and its API return no phone and no email. The live contact model is a brokered relay whose own docstring states a "hard contract … NO response below MUTUAL_OPTIN status contains owner OR finder phone/email/raw contact/exact coords". This legacy endpoint still implements the policy the product abandoned.

— The team already fixed this exact bug class. __tests__/api/reports-id-pii.test.js locks /api/reports/[id] against "a PII harvest of distressed owners" and states the rule: "assert on the raw API payload, not the rendered UI — the cruelest leaks are fields the screen hides but the JSON still ships." That is precisely this bug, on the route nobody re-checked. Verified side by side: the tested route is clean, this one leaks.

— No test covers this endpoint.

There is a second path

app/api/database/route.js:86-89 attaches the reporter's name, phone and email to every case for any caller with a session — and the route has no take, skip or limit, so it returns the whole table. Reproduced with an ordinary non-admin member:

GET /api/database -> 200, total: 8, isAuthenticated: true
  CASE-2026-154069  | Owner   | owner2@localdev.test
  FOUND-2026-935833 | Finder3 | finder3@localdev.test
  CASE-2026-920351  | Owner3  | owner3@localdev.test

Because registration has no working CAPTCHA (H1), "any session" is one signup away. The same dataset is exposed twice: once with no credential at all, and once behind a free account.

Fix. Drop contact from the public endpoint, or gate it behind a session and the relay's opt-in state. Paginate /api/database and drop the contact fields, or scope them to the case's own participants. Extend the existing regression test to cover both.
B2The lost-pet report intake runs bcrypt inside a 5-second transaction, and 500s▸

app/api/reports/create/route.js:95 opens an interactive transaction with no options, so it gets Prisma's default 5000 ms timeout. The callback runs 157 lines, and at lines 124, 129 and 134 it awaits bcrypt.hash(…, 12) — CPU-bound, event-loop-blocking, roughly 250–500 ms each.

Three sequential anonymous reports, idle local database

req1 -> 200
req2 -> 500   Transaction already closed: the timeout for this
req3 -> 200   transaction was 5000 ms, however 7483 ms passed

On a network-attached production database under concurrency this gets worse, not better. This is the single most important write in the product — a person reporting that their pet is missing — and it fails intermittently.

Fix. Hash the password before opening the transaction. Keep the transaction to the writes.
B3The entire Alerts feature is dead, list and detail▸

Both halves are broken, independently.

The list sends status=OPEN, but the CaseStatus enum has no such value — it is ACTIVE, IN_PROGRESS, SIGHTING_REPORTED, REUNITED, CLOSED_OTHER. Reproduced: the request returns 500 {"error":"Failed to list public cases"}.

The detail page reads data.case from a response that returns the case at the top level. The resulting TypeError is caught and turned into a redirect away from the page. Confirmed in the sweep both logged out and logged in, with the console error Cannot read properties of undefined (reading 'lastSeenAt').

These are the deep-link targets for "a pet was spotted near you" notifications. Rechecked on a quiet server to rule out load: still broken.

Fix. Send a real status value; read the response at the top level. Add a test that loads an alert by id.
B4City landing pages publish randomly generated "Pets Reunited" numbers▸

app/lost-pet/[location]/LocationPageClient.js:52-57

// Mock stats for now
setStats({
  activeMissions:  Math.floor(Math.random() * 50) + 10,
  reunited:        Math.floor(Math.random() * 200) + 50,
  activeSearchers: Math.floor(Math.random() * 100) + 20,
});

Rendered as three stat cards labelled "Active Missions", "Pets Reunited" and "Active Searchers".

Four consecutive loads of /lost-pet/austin-tx

load 1:  0,   0,   0    (pre-effect)
load 2: 30,  60, 116
load 3: 30, 149,  42
load 4: 53, 177,  79

"Pets Reunited" went 60 → 149 → 177 on three refreshes of the same page. These pages are public and marked index, follow. Worse, the route accepts any slug — /lost-pet/asdfghjkl-qq returns 200 with the title "Lost & Found Pets in Asdfghjkl, QQ" — so the fabricated claim can be generated for any string, indefinitely.

This is a fabricated performance claim on an indexed page, and it is discoverable by pressing F5.

Fix. Query the real numbers, or remove the cards. Then either validate the slug against the city list and 404 unknown ones, or mark them noindex.
B5On a phone, the case page's sighting button is not clickable▸

Measured at 390 × 844 on a real case page

Before scrolling
  "I've Seen Max" CTA at top: 1010px in an 844px viewport
  — 166px below the fold.

After scrolling
  sticky CTA container   top 743 → 844   (101px, z-index 40)
  global tab bar         top 779 → 844   ( 65px, z-index 50,
                                           background: white)

Hit test at the centre of the CTA:  ctaContainsHit = false

The tab bar is opaque and sits above the sticky CTA. It covers 65 of the CTA's 101 pixels, and a tap at the CTA's centre hits the tab bar and navigates away.

A neighbour who just spotted the dog opens the shared link, scrolls, taps the one button that files a sighting — and gets sent somewhere else.

Fix. Raise the CTA above the tab bar and add bottom padding equal to the tab bar height plus the safe-area inset, or suppress the tab bar on case detail. Verify by tapping the centre point, not by looking at it.
B6Nothing reports errors in production▸

app/lib/errorTracking.js is a stub. Every Sentry call in it is a comment, @sentry/* is not in package.json, and the init function is never called anywhere. Exactly one file imports the module. There is no global-error.js.

A server-side exception in production goes to stdout and nowhere else. No alert, no aggregation, no ownership.

This is a blocker because of what it does to the others: B2 and B3 are exactly the kind of failure that would ship, run for weeks, and be discovered only when a user complains — and B2's victims are people whose report silently failed, who have no reason to come back and tell you.

Fix. Wire up any error tracker before launch. This is an afternoon.
B7An anonymous stranger can file a report under any existing account▸

app/api/reports/create/route.js:96-99 looks up the submitted email and, if a user exists, attaches the case to them. Nothing verifies that the submitter controls that address. Lines 102-104 then copy that user's phone number out of their profile onto the case.

Reproduced — one unauthenticated POST using a real member's address

POST /api/reports/create
  {"email":"sarah@localdev.test", "firstName":"NotSarah",
   "petName":"ImpersonationTest", ...}              -> 200

cases attached to sarah@localdev.test:  before = 1   after = 2

GET /api/public/missions/CASE-2026-675159    (no cookie)
  petName: ImpersonationTest
  contact: {"name":"NotSarah", "email":"sarah@localdev.test"}

So a stranger can publish a fabricated lost-pet report in a real person's name, on their account, with their email exposed publicly — and it appears in the victim's own alerts page. Combined with B1 their stored phone number is published too, and with H1 (no CAPTCHA, 60/min/IP) this is automatable.

Fix. For an anonymous submission, do not bind to an existing account. Create the case against a pending identity and require an emailed confirmation before linking it to a user — as the found-pet relay already does for contact exchange.

High

Real user-facing damage, survivable for a week.

H1CAPTCHA is not wired up; report intake is limited only to 60/min/IP▸

The codebase implements real reCAPTCHA verification. No API route calls it — there are zero call sites. The only gate does nothing unless an env flag is set, and even then it only checks the header is present, never verifies the token; x-recaptcha-token: anything passes.

Report intake is absent from the rate-limit config, so it falls to the default 60/min/IP — and each call creates a user row and sends email.

Reproduced

Three anonymous POSTs created three real public cases ("Ghost1", "Ghost3", at "123 Fake St") with no CAPTCHA, no account and no moderation. They appear on the public corkboard and pushed the homepage "N pets waiting to come home right now" counter from 3 to 7. Rate-limit state is an in-memory map — per-instance, reset by every deploy.

H2A new report never announces itself to the local Rescue Force▸

Two independent bugs in the same block, both swallowed by one try/catch.

The announcement text interpolates a bare caseNumber, but that variable is declared inside the transaction callback and is out of scope there. Reproduced in the dev log on every report: Failed to create mascot post: ReferenceError: caseNumber is not defined.

Separately, the write sets isSystemPost and isPinned on a model that has neither field — confirmed in both the Prisma schema and the raw migration DDL. It would throw even with the first bug fixed.

Verified: test reports created zero squad posts. The community-mobilisation loop — the product's whole differentiator — silently does not run.

H3The Hub reports zero threads forever, and returns 200 saying it succeeded▸

The stats endpoint filters on isDeleted for both forum threads and posts. Neither model has that field. The query rejects, and the catch returns HTTP 200 with success: true and every count hardcoded to zero.

Reproduced — the database holds 1 thread and 3 categories

{"success":true,"stats":{"totalThreads":0,"totalPosts":0,
 "totalMembers":0,"totalCategories":0},"categories":[]}

The Hub is one of five links in the frozen universal navbar, and the homepage sells it as "A community, not just an app". Every visitor who clicks it finds a dead forum. Because it answers 200 saying it succeeded, nothing can detect it.

H4/my-alerts is the most broken page in the product▸

Three defects on the page where an owner goes to mark their pet found.

It prints 📍 undefined, undefined. The location line falls back to city, state, but the Case model has none of city, state or lastSeenLandmark — those fields belong to a nested relation. The fallback always renders the literal string. Another component in the same codebase already guards this correctly.

Its filters can never match. "Active" filters on OPEN/ACTIVE_SEARCH and "Found" on RESOLVED — none of which are real status values. Both tabs are permanently empty, and status labels fall through to the raw enum, so owners see IN_PROGRESS.

It is off-brand: royal-blue header bar, bootstrap-red button.

H516 of 26 admin pages bounce to /dashboard on any hard load▸

The guard runs while the session is still loading, when session is undefined — so the role check is true and it redirects before the session ever resolves. There is no loading guard. Reproduced this run on three admin routes. Bookmarks and refreshes are broken for admins; only in-app navigation works.

H6Login submits the password in the URL before React hydrates▸

The form has an onSubmit handler but no action and no method. React's handler only binds after hydration; before that the browser performs its default submit — a GET with the fields as query parameters.

Captured verbatim during the sweep

navigated to ".../login?email=admin%40localdev.test
                       &password=LocalDevScreenshots1%21"

The password then lives in browser history, in any proxy or CDN access log, and in the Referer header of later requests. Adding a hydration wait made the sweep log in cleanly, which confirms the mechanism. Same pattern on forgot-password and reset-password — where the leaked field is the new password.

H719 production-runtime vulnerabilities, 3 critical, in the auth chain▸

npm audit --omit=dev: 19 total — 3 critical, 12 high, 4 moderate.

Critical: next-auth 4.24.13 and @auth/core — "Email normalizer validates the address before Unicode normalization, allowing a homoglyph @ bypass". High: jws 3.2.2 "Improperly Verifies HMAC Signature"; axios SSRF; next 14.2.33 DoS.

CI runs npm audit … || echo, so this has been green the whole time.

H8Sitemap and robots.txt point at the retired domain; the SEO pages are in neither▸

All 16 URLs in the sitemap are on petrecovery.org. The canonical host is www.reunitepets.org — middleware 301s the old host — so every declared URL redirects. robots.txt declares two sitemaps, both on the old domain.

The sitemap lists /cases (verified 404) and /database (a redirect stub), and not one city landing page — though those are the primary organic acquisition surface.

H9The push-notification prompt interrupts every screen, including the crisis ones▸

The provider excludes only login and register. It fires 3 seconds after any authenticated page load on every other route. On mobile it renders full-width at the bottom, covering roughly 40% of a 390 × 844 viewport and the whole tab bar.

Captured over: step 1 of the lost-pet report wizard, a still-loading pets list, a still-loading Mission Control, the message composer, and every admin screen.

H10"Delete Account" is a shipped button that does nothing▸

A red "Danger Zone" button whose confirm dialog says "This action cannot be undone", which then shows a toast: "Account deletion is not yet implemented. Please contact support." — with // TODO: Implement account deletion inline. No account-deletion route exists anywhere.

The privacy policy says users may request deletion by contacting you, so the policy survives — but the UI actively misrepresents, and there is no deletion pipeline at all.

H11No unsubscribe link on any outbound email▸

An unsubscribe endpoint exists, but nothing links to it. No template references it, and the mailer adds no footer and no List-Unsubscribe header. Eight templates, zero opt-outs.

SMS, by contrast, is handled correctly — STOP/START/UNSUBSCRIBE are all implemented. Beyond compliance, a missing List-Unsubscribe header hurts inbox placement at launch volume.

H12Transactional email is on the old brand and admits an unbuilt feature▸

The notifications module — imported by eight or more live routes including found-pet reports and sightings — brands all eight templates PetRecovery.org. The SMS opt-out copy says "PetRecovery SMS alerts". A public page still reads "When you see Sarama on PetRecovery".

And one email carries the subject "Welcome to ReunitePets.org — Verify Your Email" with the body "Email verification link will be sent separately (coming soon)." There is no link.

Page titles and OpenGraph tags are correct, and case pages serve the pet's photo as the preview image — the link-preview system itself is fine.

H13Support address is on the retired domain, including in the Terms and Privacy Policy▸

support@petrecovery.org is hardcoded on the contact page, the terms page and the privacy policy. On contact it is the single largest CTA, labelled "Monitored 7 days a week", on a site branded ReunitePets throughout.

A support address on a different domain from the site is one of the specific things people check for legitimacy — and it is the contact of record in two legally binding documents.

H14/care overstates a study its own footnote contradicts▸

The page claims pets with records ready "are reunited up to 20 times more often". Three lines below, its own source note says the study "found microchipped pets returned 2.5 times more often for dogs and 20 times for cats". The headline generalises the cat figure to all pets.

H15/admin/auto-migrate runs raw DDL on page load, with no button▸

An effect calls the migration as soon as a session resolves — commented // Auto-run migration. Navigating to the URL, or hitting browser-back onto it, POSTs the migration endpoint.

High and not blocker because the endpoint is properly guarded (the role is re-read fresh from the database) and every statement is additive and idempotent, so it cannot drop data today. But it is a page that fires $executeRawUnsafe against production on navigation, duplicating what the boot command already does. One careless edit makes it destructive.

H16Nobody can read the Terms or the Liability Waiver they are accepting▸

The consent page renders {doc.content} inside the "Read Full Text" disclosure. The legal-documents API returns only id, slug, type, version, title, summary, publishedAt — there is no content field. Expanding the Terms of Service or the Liability Waiver opens an empty box.

Users are asked to accept two binding documents they are structurally unable to read, and the waiver is the one that gates physical volunteer searching. A waiver the signer could not read is hard to enforce.

Related gap: the patrol sign-up does have a waiver step with a checkbox, but the zero-friction join page — the link a stranger taps from a text message to join a physical search — has no waiver reference at all.

H17/api/sarama is an unauthenticated proxy to a paid LLM API▸

The route has no session check, and grep -c rateLimit on the file returns 0 — it imports no rate limiting at all. It reads the Anthropic key and posts to the API.

Verified — an unauthenticated POST passes every gate and reaches the handler

POST /api/sarama  (no cookie)  -> 500
{"error":"Sarama is not configured. Please add ANTHROPIC_API_KEY ..."}

It fails here only because this environment has no key set. In production, where the key is set, that same anonymous request issues a paid call. Only the middleware default of 60/min/IP applies — expensive at that rate, and trivially distributed.

The codebase already knows the right pattern: the pet-analysis route and the photo-comparison library both use a rate limiter and a global per-minute cost ceiling. This route is the outlier.

H18A destructive schema delta takes the site down instead of failing safe▸
"start": "prisma db push --skip-generate
          && node prisma/sync-legal-docs.js
          && next start"

prisma db push exits non-zero when it detects a change it will not apply without --accept-data-loss. Because the chain is &&, the server never starts — a schema delta the tool considers destructive takes the whole site down at deploy rather than deploying the previous behaviour.

It also means every deploy mutates the production schema before the app boots, with no migration history, no review step and no rollback path.

H19The PWA is never actually installable▸

The manifest exists but there is no <link rel="manifest"> in the rendered HTML and no reference in the root layout. No theme-color meta either. Its start_url is /dashboard — a protected route — so an installed app would open on a login redirect, and its icons are on the CDN rather than same-origin.

The service worker is registered only inside the push flow, so offline caching and the offline page never activate for a normal visitor.

What is genuinely good

This is not a project in trouble. Several parts are better than they need to be.

  • The shelter surface is the most finished thing here. The pitch page leads with "Shelter software that costs nothing", a concrete subhead, and a real screenshot of the actual portal. The portal itself opens on a "Needs attention" list of specific, actionable items in plain language: "Rufus and Clover have no photos yet. Adopters scroll past empty squares, and photo matching can't run."
  • Mission Control delivers on the differentiator — live counts, the sighting CTA in the primary slot, ways to help, activity log, "Found Max? Mark as reunited", and a visible exit.
  • The homepage holds up at every viewport. Both primary actions are fully visible above the fold on a 390px phone as large, thumb-friendly pills.
  • The report wizard is well built — a clear step rail, one question per step, an X to leave, big touch targets.
  • The email layer is thoughtfully engineered: a Resend → SMTP → loud-no-op provider chain, and deliberate HTML escaping with a written rationale about a pet's name turning a domain-authenticated email into a phishing relay.
  • The security posture is better than the docs suggest. Several routes the internal map lists as unauthenticated now return 401. The destructive squad wipe has a two-step confirm plus a literal type-YES gate, and its API re-reads the role from the database rather than trusting the token.
  • Link previews work. Case pages serve the pet's photo as the preview image with correct per-entity titles — the thing that decides whether a shared link helps.
  • Some error states are already right and can be copied to the broken ones: "Case not found" ships a proper card with a way out, and the wrong-password login says what happened while staying on brand.
  • The AI that ships is real — a genuine vision call with a global per-minute cost ceiling, not the mock modules sitting beside it.

  • "The case page overflows the phone viewport and scrolls sideways." Measured false. At 390 × 844 on six routes, scrollWidth === clientWidth === 390 and overflow-x is clip on both html and body. The only element past the right edge is the closed mobile drawer, correctly parked off-canvas. Playwright's full-page raster expands to include off-canvas fixed elements — a capture artifact, and also what read as "a half-drawn menu bleeding in".
  • "Wipe All Squad Data is one unguarded click." False — two-step confirm plus a literal type-YES gate.
  • "The pet edit form has no way to save." Mostly false — a save bar appears once the form is dirty. The real, smaller point: on an untouched form the only visible action is the destructive one.
  • "Eight routes end in an indefinite spinner." Only the alert detail page is genuinely broken. The others render fine on a quiet server; those captures were taken while ten subagents and a browser sweep were hitting one dev server.
  • "The public missions API is pathologically slow." My own measurement error — 13–16 s under that same contention, 0.13 s on a quiet server. The query is a single findMany plus count with an explicit select.
  • The 3 MB US-cities JSON never reaches the client bundle — only two server-side routes import it.
  • Structured logging exists and is used, in 52 API route files, alongside ~866 raw console calls.
  • The committed production env file contains placeholders only. No live secret is committed.
  • The random-value AI modules are labelled as mocks by the real implementation's own docstring and are reachable only through a session-gated route. Cleanup ticket, not a finding.
  • Many admin routes do their own fresh database role check without using the shared helper — so "lacks the helper" is not by itself a finding.

One note on the repo's own docs

The roadmap says "MVP Complete ~95%", the vision doc says "~45%", and the reality-check doc says "~35%". The code supports none of them cleanly. The surface is close to complete — 104 page files, 281 API routes, a passing build and a green suite — while operational readiness is not: no error tracking, no lint, CAPTCHA unwired, several primary features silently broken. Treat feature completeness and launch readiness as two separate numbers. The app map is stale in places too — several routes it lists as unauthenticated are now gated, and the mobile app has been rewritten from Capacitor to Expo and is a foundation, not a shippable app. Read it as a map, not as truth.
